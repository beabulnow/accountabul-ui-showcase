# Verifiabul ID — ecosystem single sign-on

Verifiabul is the identity hub for the Verifiabul family of apps. A person signs
up once here; every other app sends them to Verifiabul to sign in and receives
back only the basic profile fields that person consented to share.

Shared fields (scopes):

| Scope | Field |
| --- | --- |
| `profile.avatar` | Profile photo URL (signed, short-lived) |
| `profile.name` | `first_name`, `last_name` |
| `profile.phone` | `phone_e164` |
| `profile.email` | `email` |

Nothing else crosses app boundaries. Property registrations, documents and
verification reports stay in the app that owns them.

## Data model

| Table | Purpose |
| --- | --- |
| `public.ecosystem_apps` | Registered apps: slug, name, description, allowed return URLs, hashed client secret |
| `public.app_consents` | One row per user × app; `granted_at` / `revoked_at` |
| `public.consent_events` | Append-only audit trail, written by trigger |
| `public.identity_auth_codes` | One-time handoff codes (service-role only) |
| `public.profiles.ecosystem_consent_at` | When the user accepted the sharing notice |

## Registering a new app

Run a migration (or an admin SQL statement) that inserts the app and its
secret hash. The secret itself is generated by you and stored in the partner
app's own environment — Verifiabul only keeps the SHA-256 hash.

```sql
insert into public.ecosystem_apps (slug, name, description, home_url, redirect_urls, client_secret_hash)
values (
  'verifiabul-insights',
  'Verifiabul Insights',
  'Market and property intelligence dashboards.',
  'https://insights.example.com',
  array['https://insights.example.com/auth/verifiabul'],
  encode(digest('<the client secret>', 'sha256'), 'hex')
);
```

`redirect_urls` is an exact-match allowlist. A return URL that is not listed is
rejected.

## Flow

```text
partner app                verifiabul                        partner server
-----------                ----------                        --------------
send user to  ---------->  /connect?app=<slug>&return=<url>
                           sign in (email or Google)
                           consent screen (first time only)
              <----------  302 <return>?code=<one-time code>
                                                             POST /api/public/identity/profile
                                                             { code, client_id, client_secret }
                                                    <------  { user_id, email, first_name, ... }
```

### 1. Send the user

```
https://verifiabul.com/connect?app=verifiabul-insights&return=https://insights.example.com/auth/verifiabul
```

Optional `state` parameter is echoed back on the redirect.

Verifiabul handles sign-in, profile completion and the consent screen. When the
user confirms, they are redirected to `return` with `?code=...` (plus `state`
when supplied). If the user declines, the redirect carries `?error=access_denied`.

### 2. Exchange the code (server to server)

```http
POST https://verifiabul.com/api/public/identity/profile
Content-Type: application/json

{
  "code": "…",
  "client_id": "verifiabul-insights",
  "client_secret": "…"
}
```

Response:

```json
{
  "user_id": "8f0…",
  "scopes": ["profile.avatar", "profile.name", "profile.phone", "profile.email"],
  "profile": {
    "email": "person@example.com",
    "first_name": "Jane",
    "last_name": "Doe",
    "phone_e164": "+13144455111",
    "avatar_url": "https://…"
  }
}
```

Rules enforced by the endpoint:

- The code is single-use and expires after 5 minutes.
- The code is bound to the app that requested it; another app's secret fails.
- The consent must still be active at exchange time — a revoked grant returns
  `403 consent_revoked` even with a valid code.
- Only consented scopes are returned; a missing scope means a missing field.
- The client secret is never accepted from a browser; call this from your
  server.

Use `user_id` as the stable link between your app's local user record and the
Verifiabul identity. Do not treat email as the key — people change it.

## Revocation

Users manage access from **Profile → Connected apps**. Revoking sets
`revoked_at`, which immediately blocks future code exchanges for that app. Data
your app already stored locally is yours to purge — honour deletion requests.
